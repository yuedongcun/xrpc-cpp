# 服务端性能上限分析

> 本文是早期纯原始负载压测的历史分析。当前分层压测口径、类型化 RPC 稳态结果和对外数据请以
> `docs/current_benchmark_results.md` 为准。

本文记录服务端 QPS 优化之后，怎样判断是否已经找到性能上限，以及什么时候才可以说“下一步提升主要靠换机器”。

## 当前设置

- 负载：`raw`
- 客户端模式：`firehose`
- 服务端线程：`worker_threads=3`，`connection_io_threads=3`
- CPU 亲和性：服务端 `0,2,4`，客户端 `6,8,10`
- 服务端 CPU 预算：`3 * 100% = 300%`
- 客户端 CPU 预算：`3 * 100% = 300%`
- 机器：Intel Core i7-9750H，6 物理核 / 12 逻辑 CPU，WSL2
- 性能测试服务端输出的背压设置：
  - `max_inflight_per_connection=128`
  - `max_pending_jobs_global=10000`
  - `max_write_queue_bytes_per_connection=8388608`

本文中的 CPU 利用率按下面方式计算：

```text
server_cpu_budget = number_of_server_cpus * 100% = 300%
server_budget_utilization = server_cpu_percent / server_cpu_budget
```

例如，`235.27%` 服务端 CPU 表示使用了 `235.27 / 300 = 78.4%` 的已绑定服务端 CPU 预算。

## 当前数据说明了什么

原来的最终矩阵使用 `firehose_connections=3`，最高只跑到 `firehose_inflight=384`。
这个值刚好等于 `3 * 128`，也就是 3 个连接在当前每连接 in-flight 限制下的最高健康深度。
这个点上，最终测试达到 273k 到 293k QPS，但服务端 CPU 只有 184.73% 到 205.43%，
明显低于 300% 的预算。

如果只提高 total in-flight，但不提高连接数，首先撞到的是每连接 in-flight 限制，而不是硬件上限：

- `3 conn / 512 inflight` 超过 `3 * 128`，出现失败。
- `6 conn / 1024 inflight` 超过 `6 * 128`，出现失败。
- `6 conn / 768 inflight` 正好等于 `6 * 128`，0 失败，达到 324858.50 QPS。

提高连接数并保持每连接在途请求数不超过 128 后，得到的健康吞吐扫描如下：

| 连接数 | 在途请求数 | 成功 QPS | 失败数 | p99（毫秒） | 服务端 CPU | 服务端预算使用率 | 最高服务端线程 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 6 | 768 | 324858.50 | 0 | 4.94 | 194.40% | 64.8% | 48.27% |
| 9 | 1152 | 322709.64 | 0 | 8.42 | 204.61% | 68.2% | 47.59% |
| 12 | 1536 | 361715.76 | 0 | 8.66 | 212.16% | 70.7% | 49.37% |
| 18 | 2304 | 410378.80 | 0 | 12.82 | 231.45% | 77.2% | 56.85% |
| 24 | 3072 | 416443.14 | 0 | 14.10 | 216.53% | 72.2% | 50.48% |
| 36 | 4608 | 454093.29 | 0 | 18.42 | 232.54% | 77.5% | 54.93% |
| 48 | 6144 | 422463.37 | 0 | 27.30 | 216.22% | 72.1% | 51.22% |
| 72 | 9216 | 472721.44 | 0 | 32.17 | 235.27% | 78.4% | 55.55% |
| 78 | 9984 | 440629.09 | 0 | 38.32 | 216.98% | 72.3% | 51.66% |

当前观测到的纯吞吐峰值是：

- `72 conn / 9216 inflight` 下达到 472721.44 QPS
- 0 失败
- p99 32.17 ms
- 服务端 CPU：235.27% / 300% = 78.4%
- 客户端 CPU：222.07% / 300% = 74.0%

这个结果是高排队深度下的吞吐峰值，不是机器上限的证明。服务端仍然没有用满已绑定的 CPU 预算。
后一个点 `78 conn / 9984 inflight` 已经接近全局待处理请求限制，并且吞吐变差，所以当前扫描找到的是
当前设置和流量形态下的队列深度峰值，而不是硬 CPU 上限。

## 实际容量取决于服务等级目标

如果没有延迟服务等级目标，最高 QPS 很容易误导判断，因为它可能只是靠增加排队延迟换来的。
基于当前单轮数据，可以先把容量临时分成下面几档：

| 定义 | 当前最佳观测点 | 容量 |
| --- | --- | ---: |
| p99 <= 5 毫秒，0 失败 | `6 conn / 768 inflight` | 324858.50 QPS |
| p99 <= 10 毫秒，0 失败 | `12 conn / 1536 inflight` | 361715.76 QPS |
| p99 <= 15 毫秒，0 失败 | `24 conn / 3072 inflight` | 416443.14 QPS |
| 只看吞吐，0 失败 | `72 conn / 9216 inflight` | 472721.44 QPS |

这些是不同服务质量定义下的容量点。只有最后一个是纯吞吐峰值，而且它已经用明显更高的 p99 换取了更多 QPS。

## 什么时候可以说机器是上限

在当前 CPU 亲和设置下，“服务端 CPU 饱和”应该指服务端接近 300% 的绑定 CPU 预算，
而不是单纯看到 QPS 停止增长。一个实际可用的阈值是：

```text
server_cpu_percent >= 270%  # 至少用到 3 个绑定逻辑 CPU 的 90%
```

只有同时满足下面条件时，才适合说当前机器是下一步瓶颈：

1. 先固定容量定义：是只看吞吐且 0 失败，还是要求 p99 <= 10 毫秒 / p99 <= 15 毫秒这类服务等级目标。
2. 施加的负载足够高，但没有违反已配置的背压：
   `firehose_inflight <= firehose_connections * 128`，并且总在途请求数不超过全局待处理请求限制，
   除非这次测试本来就是在测过载行为。
3. 多轮重复结果进入平台期：继续提高施加的负载至少两个档位，成功 QPS 中位数变化小于 3% 到 5%。
4. 服务端 CPU 已经饱和：服务端 CPU 中位数至少达到 270% / 300%。如果总 CPU 明显偏低，但某个必要服务端
   线程接近 90% 到 100%，那首先是软件或架构瓶颈，不是买更快机器的理由。
5. 客户端不是瓶颈：客户端 CPU 没接近自己的 300% 预算，没有必要的客户端线程被打满，并且换用第二个
   负载生成器后服务端 QPS 不再上升。
6. 性能剖析不再显示明显可修的软件热点，例如可避免的分配、过小写入、过多任务转交、锁竞争或连接分布不均。
7. 结果在频率、温度、CPU affinity、后台负载都受控的情况下，多次重复仍然稳定。

只有这些条件成立之后，才应该得出“如果要继续提升这个 workload，就需要更多 CPU、更快 CPU，或者换机器”的结论。

## 当前结论

当前数据不支持“下一步就是换机器”。

目前观测到的纯吞吐最佳点是 472721.44 QPS，但它只使用了 78.4% 的绑定服务端 CPU 预算，
最热服务端线程也只有 55.55%。用这个点做一个粗略 CPU 外推：

```text
qps_per_full_logical_cpu = 472721.44 / 2.3527 = about 200900 QPS
90% server CPU line = 200900 * 2.7 = about 542000 QPS
100% server CPU line = 200900 * 3.0 = about 603000 QPS
```

这个外推不是承诺 XRPC 一定能达到 542k 到 603k QPS。它只是一个合理性检查：
如果系统在 440k 到 473k QPS 左右平台化，但服务端 CPU 仍然只有 216% 到 235%，
那瓶颈就不是物理 CPU 预算。下一步应该先查软件侧：事件循环分布、工作线程任务转交、批处理、
写队列排空、分配器与协议开销、排队策略，或者性能测试的流量形态。

今天最准确的说法是：

> 在当前设置下，已经观测到的无失败 raw-throughput 峰值约为 473k QPS，但这是队列深度和流量形态下的峰值，
> 不是已确认的机器上限。要声称机器是上限，需要服务端在当前 3 CPU 亲和设置下平台化到接近或超过
> 270% 服务端 CPU，同时排除客户端和已配置背压的影响。
