# XRPC 注释规范

XRPC 源码注释统一使用英文，目标是帮助未来维护者安全地修改代码。本文用中文说明何时以及如何添加注释。

## 应该注释什么

- 头文件 API 契约：类或结构体的用途、调用方义务、所有权、阻塞行为、线程安全和返回语义。
- 复杂模块的设计说明：关键边界、所有权模型、状态机、线程模型和失败语义。
- 公开 API 契约：生命周期、所有权、阻塞行为、线程安全、错误语义和兼容性预期。
- 内部不变量：状态机规则、队列所有权、callback 顺序、buffer 生命周期和跨文件共享假设。
- 协议和线格式约束：frame 边界、版本假设和影响兼容性的决策。
- 性能取舍：不直观的常量、批处理、分配规避和 hot path 快捷路径。
- 失败行为：错误是关闭连接、取消工作、返回 status，还是抛出异常。

## 不应该注释什么

- 不要复述普通代码流程。
- 不要用文字重复函数名、变量名或明显的类型信息。
- 不要用注释弥补含糊命名或可避免的复杂度。
- 如果一处文件级或类级设计说明更清楚，不要把设计理由散落成许多小注释。
- 除非缺口具体且可执行，否则不要添加 TODO。
- 不要描述代码没有真正保证的行为。

## 设计说明

当文件或核心类型的行为无法仅从局部代码恢复时，应在文件开头或核心类之前添加设计说明。典型场景包括：

- coroutine 运行时所有权与完成规则；
- `io_uring` operation 生命周期和 callback 顺序；
- RPC session 分帧与请求/响应错误映射；
- 服务端生命周期状态转换；
- 客户端端点发现、路由快照和重试安全性；
- 背压计数和关闭行为。

设计说明应该解释稳定模型，而不是实现细节，并保持足够简短，使维护者愿意在设计变化时同步更新。

推荐形式：

```cpp
// Design note:
// - Ownership: ...
// - State: ...
// - Threading: ...
// - Failure: ...
```

只保留与文件相关的条目。如果解释超过一个短代码块，应把长文移到 `docs/`，源码中只保留链接。

## 头文件 API 注释

公开头文件和重要内部头文件使用 Doxygen 注释，通常形式为：

```cpp
/**
 * @brief One-sentence purpose of the type or method.
 *
 * Extra contract details: ownership, lifetime, thread safety, failure behavior,
 * compatibility constraints, or performance tradeoffs that are not obvious from
 * the signature.
 *
 * @param value What the caller must provide.
 * @return What the caller can rely on.
 */
```

如果 struct 的公开字段属于 API 契约、线格式、诊断快照或跨模块状态，使用简短的 `/** @brief ... */` 字段注释。微小的局部辅助 struct 如果名称已经表达完整含义，则不强制逐字段注释。

头文件中的函数声明默认应有一条简短注释。私有 helper 如果名称无法表达其生命周期、锁、重试或所有权影响，也应注释。平凡的 deleted/defaulted 特殊成员函数不需要注释，除非 move/copy 行为本身属于公开契约。

简单 adapter 或常量使用短 Doxygen 注释即可，目标是帮助读者，而不是让每个小文件膨胀。

## 风格

- 头文件 API 使用 Doxygen block，局部实现细节使用简短 `//` 注释。
- 局部注释使用一到三个完整英文句子。
- 需要说明多个不变量时，在类或 struct 前使用紧凑的 `//` block。
- 注释解释规则存在的原因，不复述今天碰巧采用的每个步骤。
- 修改使注释失效时，必须在同一修改中更新或删除注释。

## 审查清单

添加注释前，确认它至少回答下面一个问题：

- 调用方必须维持什么契约？
- 哪个不变量在维护时容易被破坏？
- 为什么这里没有采用看似最直接的实现？
- 哪个并发、生命周期或所有权规则无法从类型直接看出？
- 哪种失败或取消行为依赖当前顺序？
