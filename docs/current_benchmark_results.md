# 当前性能测试方法与结果

本文记录 2026-07-30 测得的可复现结果及其测试边界。历史优化实验采用不断变化的 raw-only 口径，不能与本文结果直接比较。

## 测试分层

性能测试分别回答三个问题：

1. **Typed Firehose** 衡量服务端容量。发压器发送预序列化的 `EchoRequest` frame，并校验完整响应字节。生产服务端仍会执行分帧、RPC header 解析、方法查找、Protobuf 请求解析、handler 分发、Protobuf 响应序列化和响应组帧。这覆盖完整服务端 RPC 路径，但有意排除生产客户端开销。
2. **Production RpcClient** 调用公开的类型化 `RpcClient::Call()` API，包含客户端 Protobuf 编码、路由、连接复用、请求与响应匹配、响应解码和同步调用者唤醒。该测试描述正常端到端客户端行为，不用于推断服务端吞吐上限。
3. **Raw Firehose** 绕过类型化服务注册表和 Protobuf payload 处理，只隔离分帧、网络、worker 调度、背压和响应写出，因此仅代表传输层与运行时的上界。

## 测试环境

- CPU：Intel Core i7-9750H，6 个物理核 / 12 个逻辑 CPU
- 运行环境：WSL2、Linux loopback
- 服务端亲和性：逻辑 CPU `0,2,4`，对应物理核 `0,1,2`
- 客户端亲和性：逻辑 CPU `6,8,10`，对应物理核 `3,4,5`
- 服务端：3 个 worker 线程和 3 个 connection I/O loops
- Payload：128 字节 Echo message 字段；编码后的 Protobuf payload 还包含字段元数据
- 结果策略：每轮启动全新服务端，正式测量前预热，精确校验响应，报告 3 轮中位数
- 矩阵策略：按 repetition 交错执行 case，降低温度和频率变化产生的顺序偏差

所有结果均来自同机 loopback，不包含跨主机网络延迟。

## 类型化服务端容量

配置：`tools/benchmark/configs/v1_protobuf_capacity.json`。

| 总在途请求 | QPS 中位数 | p99 中位数 | 失败数 | 服务端 CPU 中位数 |
| ---: | ---: | ---: | ---: | ---: |
| 12 | 23,508 | 0.88 ms | 0 | 187.70% |
| 48 | 92,009 | 0.90 ms | 0 | 190.00% |
| 192 | 166,923 | 2.03 ms | 0 | 199.48% |
| 768 | 336,027 | 5.76 ms | 0 | 277.63% |
| 1536 | 399,078 | 8.55 ms | 0 | 293.22% |

完整曲线使用 3 秒预热和 3 轮 15 秒测量。`192` inflight 的一轮在 WSL2 下出现 `40.8 ms` p99 异常值，因此该点不应被描述为严格延迟 SLO。

两个有代表性的工作点使用 `tools/benchmark/configs/v1_protobuf_steady_state.json` 进行了 3 轮 30 秒复测：

| 工作点 | QPS 中位数 | QPS 最小值—最大值 | p99 中位数 | 失败数 | 服务端 CPU 中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 低延迟，48 inflight | 96,103 | 95,222—103,690 | 0.86 ms | 0 | 194.05% |
| 饱和点，1536 inflight | 414,743 | 389,889—452,667 | 8.08 ms | 0 | 289.30% |

六轮稳态测试均没有客户端失败、服务端背压拒绝、worker 拒绝或写队列关闭。饱和点报告中位数，是因为三轮的最小值和最大值仍相差约 15%。

## 类型化吞吐上限

上限搜索先在固定总 inflight 下改变连接数，再保持每连接不超过默认 128 inflight 的前提下同时增加连接数和 inflight。最终边界扫描使用 `tools/benchmark/configs/v1_protobuf_ceiling_boundary.json` 测试 72 到 96 条连接，总 inflight 不超过默认全局上限 10,000。最高中位数出现在 72 条连接，为 465,650 QPS；更多连接时下降到 453,671—427,120 QPS。

最终候选点使用 `tools/benchmark/configs/v1_protobuf_ceiling_verify.json` 验证：3 秒预热，3 轮交错执行，每轮 30 秒。

| 连接数 | 总在途请求 | QPS 中位数 | QPS 最小值—最大值 | p99 中位数 | 失败数 | 服务端 CPU 中位数 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 12 | 1536 | 422,391 | 401,720—457,620 | 8.14 ms | 0 | 266.72% |
| 48 | 6144 | 438,356 | 431,340—478,866 | 26.82 ms | 0 | 274.97% |
| 72 | 9216 | 466,984 | 457,345—473,937 | 35.83 ms | 0 | 274.47% |

九轮测试均没有客户端失败、服务端背压拒绝、worker 拒绝或写队列关闭。因此，测试到的最高持续无拒绝点约为 467,000 QPS。最高单轮 30 秒结果为 478,866 QPS，但不作为持续容量结论。

独立的 `tools/benchmark/configs/v1_protobuf_overload_probe.json` 通过 96 条连接提供 12,288 inflight。3 秒内成功完成 1,618,148 次调用，并在全局 pending job 上限处拒绝 85,497 次，失败率 5.02%。这证明继续加压会越过默认背压边界，而不是形成更高的可靠容量。

该结果是吞吐上限，不是推荐工作点。相较 12 条连接、1536 inflight，72 条连接的吞吐提高约 10.6%，但 p99 从 8.14 ms 增加到 35.83 ms。

## 原始运行时上界

配置：`tools/benchmark/configs/v1_raw_high_load.json`，3 秒预热，3 轮 30 秒测量。

| 连接数 | 总在途请求 | QPS 中位数 | QPS 最小值—最大值 | p99 中位数 | 失败数 | 服务端 CPU 中位数 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 72 | 9216 | 605,752 | 586,727—661,293 | 31.68 ms | 0 | 293.65% |

历史短时深队列 raw 测试曾达到约 690,000 QPS。更有参考价值的重复 30 秒中位数约为 606,000 QPS，p99 为 31.68 ms。两者都不代表持续类型化 RPC 容量。

## 结论摘要

可复现的简明结论是：

> 服务端与发压器各绑定三个物理核，使用 128 字节 Protobuf Echo workload 时，完整服务端 RPC 路径在三轮 30 秒测试中以零失败持续达到 422,000 QPS、8.1 ms p99；低于 1 ms p99 时达到 96,000 QPS。
