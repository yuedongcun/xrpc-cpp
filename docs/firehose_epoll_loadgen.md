# Firehose Epoll 发压器改造记录

本文记录性能测试 Firehose 发压器从“每连接一组读写线程”改为 `epoll` 事件循环后的设计和验证结果。

## 背景

旧 Firehose 发压器为了维持较高的在途请求数，每个连接启动两个线程：

- 一个写线程持续发送请求。
- 一个读线程持续读取响应。

这个模型容易把发压端 CPU 消耗放大。连接数提高后，线程数按 `2 * firehose_connections` 增长，例如
`72` 个连接会创建约 `144` 个读写线程。这样会带来额外调度、同步、分配和缓冲区移动成本，可能在服务端
还没被压满之前先把发压端推到瓶颈。

## 新设计

Firehose 现在只有一条发压路径：

```text
原始 Firehose
```

发压参数：

```text
--firehose_connections=N
--firehose_inflight=N
--firehose_io_threads=N
```

含义：

- `0` 表示自动选择。
- 在 `run_suite.py` 中，如果配置了客户端 CPU 亲和性，自动值会解析为当前用例可用的客户端 CPU 数量和连接数的较小值。
- 每个 epoll I/O 线程管理一组连接。
- 每个连接只归属一个 I/O 线程，连接状态不跨线程共享。

核心变化：

- 用少量 `epoll` I/O 线程替代每连接 reader/writer 线程。
- 每个连接维护自己的在途请求槽位、读缓冲区和写缓冲区。
- 请求帧直接追加到连接写缓冲区，不再为每个请求创建临时帧字符串。
- 读缓冲区使用偏移量与压缩策略，避免每个响应都调用 `erase(0, consumed)`。
- 写入方批量写入多个帧，减少系统调用次数。
- 保持原有 `firehose_connections`、`firehose_inflight`、`duration`、`payload_size` 语义。
- `runs.csv` / `summary.md` 记录 `firehose_io_threads`，便于复现实验。

## 验证环境

- 负载：`raw`
- 服务端：`worker_threads=3`，`connection_io_threads=3`
- CPU 亲和性：服务端 `0,2,4`，客户端 `6,8,10`
- 负载大小：128 字节
- 持续时间：5 秒
- 机器：Intel Core i7-9750H，6 物理核 / 12 逻辑 CPU，WSL2

## 对比结果

`threaded` 路径。

## 结论

epoll Firehose 已经达到本轮目标：

- Firehose 路径不再使用每连接一组读写线程的模型。
- 发压端 CPU 显著下降，高连接用例从 210.56% 降到 81.71%。
- QPS 没有回退，高连接用例从 430322.38 提高到 486960.48。
- 旧线程式发压实现已删除，避免继续维护两套发压模型。
- 旧阻塞式客户端性能测试也已删除，性能测试客户端只保留原始 Firehose 路径。
- 性能测试输出保留原有指标，并新增 Firehose I/O 线程数元数据。

后续如果服务端继续优化，发压端仍有进一步优化空间，例如延迟采样模式、更多批量写入策略或使用独立发压机验证。但从当前数据看，Firehose 发压端已经不再明显先于服务端成为瓶颈。
